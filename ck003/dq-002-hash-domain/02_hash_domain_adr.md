# ADR — DQ-002 Hash Domain

**Status:** PROPOSED — pending review and merge

**Decision ID:** CK-003 / DQ-002

**Scope:** Cross-language Merkle/hash-domain contract between RI-PY and RI-RS.

**Baseline specification commit:** `62d2d6bcc1a46dd505ebfe400ad01fa3c6a25bf0`

## 1. Context

The current normative corpus establishes cryptographic integrity requirements but does not yet define a complete byte-level canonical serialization/hash-domain contract for interoperability between RI-PY and RI-RS. In particular, APS-200 §8 leaves canonical serialization as TODO, while APS-300 does not mandate a concrete cryptographic algorithm.

The two current implementations use materially different Merkle/hash constructions. RI-PY currently hashes serialized/encoded event material without the RI-RS domain-separation construction. RI-RS uses raw byte domains with explicit leaf/node prefixes and RFC 6962-style tree semantics.

Therefore, identical semantic evidence cannot currently be assumed to produce identical leaf digests or Merkle roots across implementations.

## 2. Decision

Aura will use the **RI-RS construction as the canonical hash-domain model** for CK-003.

The normative construction is:

```text
canonical object
        |
        v
canonical bytes
        |
        +-- leaf --> SHA-256(0x00 || canonical_bytes)
        |
        +-- node --> SHA-256(0x01 || left_digest[32] || right_digest[32])
```

Merkle tree construction will use **RFC 6962 tree semantics**.

## 3. Normative requirements

### 3.1 Canonical byte boundary

Hashing MUST operate on one explicitly defined sequence of canonical bytes. A semantic object MUST NOT be hashed through implementation-specific object representations, language-native dictionary ordering, pretty-printed JSON, or an implementation-defined string representation.

The canonical serialization format itself is a separate CK-003 decision and MUST be specified before DQ-002 can be declared fully conformant.

### 3.2 Leaf hash domain

For a canonical byte sequence `B`, the leaf digest is:

```text
SHA-256(0x00 || B)
```

`0x00` is a mandatory one-byte domain separator and is part of the hashed input.

### 3.3 Internal node hash domain

For two 32-byte child digests `L` and `R`, the parent digest is:

```text
SHA-256(0x01 || L || R)
```

`0x01` is a mandatory one-byte domain separator and is part of the hashed input. `L` and `R` MUST be the raw 32-byte SHA-256 digests, not their hexadecimal text encodings.

### 3.4 Digest representation

The cryptographic domain uses raw 32-byte digests. Hexadecimal encoding is a presentation/transport representation only and MUST NOT be substituted for raw digest bytes inside the node-hash domain.

### 3.5 Tree semantics

Merkle tree construction and proof semantics MUST follow RFC 6962 semantics. Any deviation, including a different odd-node policy, constitutes a different tree construction and MUST NOT be silently treated as interoperable.

### 3.6 Cross-language conformance

RI-PY and RI-RS MUST produce byte-identical results for the same conformance fixture at every cryptographic boundary:

1. canonical serialized bytes;
2. leaf digest;
3. each intermediate node digest;
4. final Merkle root;
5. proof verification result where applicable.

A root-only comparison is insufficient as the sole conformance evidence.

## 4. Compatibility and migration

This ADR does **not** authorize immediate modification of RI-PY, RI-RS, or production certificate generation.

Existing RI-PY behavior that does not satisfy this construction MUST be treated as legacy/non-conformant for the CK-003 target until remediation is implemented and verified.

Existing data MUST NOT be silently re-hashed under the new domain and represented as if it were generated by the old construction. Migration of persisted evidence, if required, is a separate decision.

## 5. Security rationale

Explicit domain separation prevents ambiguity between leaf and internal-node hashing domains. Using raw child digests avoids accidental dependence on textual hexadecimal representation. RFC 6962-style semantics provide a precisely defined Merkle construction rather than leaving tree behavior to language-specific implementation choices.

## 6. Consequences

### Positive

- Establishes one cryptographic hash-domain contract for both implementations.
- Removes the RI-PY/RI-RS ambiguity at the Merkle hashing boundary.
- Enables deterministic cross-language fixtures.
- Makes CI conformance mechanically testable.
- Preserves a clear separation between canonical serialization and cryptographic hashing.

### Negative / required follow-up

- RI-PY requires remediation before it can be declared CK-003 conformant.
- Canonical serialization remains a separate normative dependency.
- Existing persisted hashes may require explicit migration handling.
- Cross-language fixtures and CI gates are mandatory follow-up work.

## 7. Rejected alternatives

### A. Keep RI-PY as canonical

Rejected because its current construction does not provide the same explicit raw-byte/domain-separated contract implemented by RI-RS and does not resolve the cross-language interoperability requirement.

### B. Keep both implementations as independent valid constructions

Rejected. A protocol-level interoperability contract cannot have two silently incompatible hash domains for the same semantic evidence object.

### C. Hash hexadecimal child strings

Rejected because the cryptographic node domain must operate on raw 32-byte digests; hashing textual encodings introduces an unnecessary representation dependency.

### D. Implement remediation before recording the decision

Rejected. The normative decision must precede production remediation so that implementation changes are evaluated against a frozen target rather than becoming the de facto specification.

## 8. Verification plan

The decision will be considered implementation-ready only after the following evidence is produced:

1. `03_cross_language_fixture` — shared fixture with exact canonical bytes and expected hashes.
2. `04_RI-PY_conformance_test` — RI-PY independently verifies the fixture.
3. `05_RI-RS_conformance_test` — RI-RS independently verifies the same fixture.
4. `06_CI_gate` — CI rejects divergence.
5. `07_DQ-002_verdict` — evidence-based closure decision.

## 9. Current verdict

**DQ-002:** DECISION RECORDED / IMPLEMENTATION OPEN / CONFORMANCE NOT YET PROVEN.

This ADR defines the target. It does not claim that either production implementation already conforms.
