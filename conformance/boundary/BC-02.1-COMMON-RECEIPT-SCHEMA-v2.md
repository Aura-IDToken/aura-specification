# BC-02.1 — COMMON RECEIPT SCHEMA v2

**Status:** CONSTRUCTED
**Parent:** BC-02 — Minimal Receiver-Side Handoff
**Supersedes for new receipts:** BC-02.1 v1 (`schema_version = 1`)
**Purpose:** BC-02.1 PRE-01 minimal schema correction — make the two B-VAL-014
digest operands independently observable and provenance-identifiable.
**Conformance execution:** BLOCKED
**B-VAL-014:** NOT EXECUTED
**§4.5:** NO RESULT
**Normative authority:** NONE

This artifact is an engineering schema correction. It introduces no normative
protocol change, no new protocol requirement, and no new fixture class. It does
not change the meaning of B-VAL-014.

## 0. Relationship to v1

BC-02.1 v1 remains unmodified and remains the historical record of the schema as
constructed at `7d1977f`, including its recorded R-VAL-001…012 construction
validation. Its `schema_version = 1` receipts, including the two receipts
produced by the Controlled P-01 Handoff, are **not** reinterpreted by this
artifact and are **not** rewritten.

v2 is a **minimal correction**, not a redesign. Everything in v1 §1, §2, §5, §7,
§8, §9, §10, §11 and §14 carries over unchanged in intent. v1 §15's
R-VAL-001…012 remain the schema-construction assertions and are **not re-run,
restated, or re-scored** by PRE-01.

### 0.1 Why the correction is required

BC-02 §14 states B-VAL-014 over two operands:

```text
receipt.receipt_digest == input_segment_sha256      on BOTH sides
receipt_digest_source  == RECEIVER_RECOMPUTED       on BOTH sides
raw_input_encoding     ∈ {identity, base64, base16}
```

BC-02.1 v1 carries **one** digest field, `received.recomputed_sha256`. Under v1
the only way to evaluate the first line is to read one field twice. That makes
the equality a tautology of the receipt's shape rather than an observation of
two independent calculations, which is the error CONF-003 §5 warns against and
which BC-02 §14.1 expressly prohibits flattening.

This gap is recorded as **PRE-01** in
`B-VAL-014-DEFINITION-RECONCILIATION-RECORD.md` §16.1. v2 closes it at the
schema layer only.

## 1. Responsibility boundary

Unchanged from v1 §1. A receipt is an **evidence input**. It is not a
conformance result.

BC-02.1 MUST NOT represent or derive PASS, FAIL, CONFORMANT, NON_CONFORMANT,
acceptance state, digest-output state, §4.5 result, or B-VAL-014 result.

Successful validation of a v2 receipt is **not** conformance and is **not** a
B-VAL-014 result.

## 2. Schema identity

```text
schema_id      = BC-02.1-COMMON-RECEIPT
schema_version = 2
```

`schema_id` and `schema_version` identify this engineering schema. They do not
identify a protocol version. The version bump exists so that a v1 receipt is
never read under v2 rules, and a v2 receipt is never read under v1 rules.

## 4. Fixture identity

`fixture_artifact_identity` is:

```text
fixture_artifact_identity = SHA-256(exact issued artifact octets)
```

recorded as 64 lowercase hexadecimal digits. It refers to the **issued
artifact**, never to a logical object reconstructed by the receiver, and never
to `hash(serialized_object)`.

`fixture_artifact_name` is a **label only**:

```text
fixture_artifact_name = FIX-DIGEST-P01.canonical.json
```

A name MUST NOT be treated as an artifact identity. v2 rejects a
`fixture_artifact_identity` that is not a SHA-256 hexadecimal digest, so a file
name can no longer occupy the identity field.

`issuance_id` identifies the issuance under which the artifact was released. It
is a distinct identity:

```text
fixture_id  ≠  issuance_id  ≠  fixture_artifact_name  ≠  fixture_artifact_identity
```

No value of any of the four may be inferred from another unless an authoritative
binding exists. **No such binding currently exists for `issuance_id`.** See §10.

### 4.1 v1 field-semantics mismatch (reported, not reconciled)

BC-02.1 v1 §4 required `fixture_artifact_identity` but did not state that its
value is a digest. Both receipts produced by the Controlled P-01 Handoff carry:

```text
fixture_artifact_identity = "FIX-DIGEST-P01.canonical.json"
```

which is, under v2 §4, an **artifact name occupying the identity field**.

This artifact records the mismatch. It does **not** rewrite those receipts, does
**not** reinterpret them as if they had carried a digest, and does **not**
declare a retroactive binding. Under v2 the two values are separate fields.

## 5. Handoff state

Unchanged from v1 §5. `handoff.status` is the closed engineering domain
`TRANSFERRED`, `NOT_TRANSFERRED`, `ERROR`. `PASS`, `FAIL`, `CONFORMANT` and
`NON_CONFORMANT` are prohibited anywhere in the receipt.

## 6. Received material and input segment — two operands, two paths

`received` records the material actually observed by the receiver.
`input_segment` records the material the digest of record is taken over after
the declared decode. They are separate groups because they are separate source
material.

```text
PATH B — actual received buffer

    received transfer unit
        ↓
    received.raw_octets                     (the actual receiver buffer)
        ↓
    SHA-256
        ↓
    digest_operands.receipt_digest.value

PATH A — input segment

    received transfer unit
        ↓
    controlled decode  (input_segment.raw_input_encoding)
        ↓
    input_segment.octets                    (the input segment)
        ↓
    SHA-256
        ↓
    digest_operands.input_segment_sha256.value
```

`input_segment.raw_input_encoding` is the closed domain taken verbatim from the
BC-02 §14 formal condition:

```text
identity
base64
base16
```

Recording the encoding is a schema record. It decides nothing about B-VAL-014.

### 6.1 Alias prohibition — R-INV-05

```text
digest_operands.receipt_digest.value
    MUST NOT be assigned from
digest_operands.input_segment_sha256.value

digest_operands.input_segment_sha256.value
    MUST NOT be assigned from
digest_operands.receipt_digest.value
```

and neither may be assigned from any other previously computed digest, including
`fixture.fixture_artifact_identity`.

Each operand MUST be the result of applying SHA-256 to the raw material named by
its own `source_material_ref`. The two values **may** be equal in a later
controlled execution. That equality is an **observed result**, never an
assignment, a copy, or an alias.

### 6.2 Digest source

`DigestOperand.source` is a closed domain:

```text
RECEIVER_RECOMPUTED
EXTERNALLY_SUPPLIED
COPIED_FROM_OTHER_OPERAND
```

For both operands the BC-02 §14 condition requires:

```text
digest_operands.receipt_digest.source        = RECEIVER_RECOMPUTED
digest_operands.input_segment_sha256.source  = RECEIVER_RECOMPUTED
```

`COPIED_FROM_OTHER_OPERAND` is deliberately **representable**. A source field
that can only hold one value records nothing; naming the prohibited case is what
makes its absence checkable rather than merely asserted. A receipt carrying it
is a receipt that has, by its own record, violated R-INV-05.

### 6.3 Source material

`DigestOperand.source_material` is a closed domain:

```text
RECEIVED_BUFFER
INPUT_SEGMENT
```

`DigestOperand.source_material_ref` names where that raw material is recorded in
the receipt, so the operand is traceable to the exact octets it was taken over:

```text
receipt_digest.source_material_ref        = "received.raw_octets"
input_segment_sha256.source_material_ref  = "input_segment.octets"
```

An operand names its material. It never carries a second copy of it, and it
never substitutes a representation for it.

### 6.4 Raw-material rule

Unchanged from v1 §6. The digest MUST NOT be computed from an expected hash, a
fixture description, a parsed object, reconstructed JSON, a textual hexadecimal
representation, or a Base64 text representation.

The logical value of `received.raw_octets` and of `input_segment.octets` is an
octet sequence. For JSON receipt transport both use **Base64** as the explicit
transport encoding of that octet sequence:

```text
JSON representation of the octets ≠ the octet sequence itself
```

The Base64 representation MUST decode unambiguously to the exact octets. Each
digest is computed over the decoded octets, never over the Base64 characters.

`received.octet_length` MUST equal the number of decoded octets in
`received.raw_octets`, and originates from the actual received buffer.
`input_segment.octet_length` MUST equal the number of decoded octets in
`input_segment.octets`. Neither length may be taken from the other group.

## 7. Operand provenance

Each operand carries its own provenance chain, so that the chain is resolvable
**from the operand**, not only from the receipt as a whole:

```text
operand
   ↓
source material            source_material, source_material_ref,
                           source_material_octet_length
   ↓
calculation path           calculation_path
   ↓
receiver                   computed_by.receiver_id
   ↓
implementation             computed_by.implementation_id
   ↓
adapter                    computed_by.adapter_id
   ↓
source commit              computed_by.source_commit
   ↓
execution environment      computed_by.environment_id
```

Together with `source`, a v2 receipt makes it determinable, per operand: what
was hashed; which receiver hashed it; which implementation was involved; which
adapter was involved; which source commit was used; which environment was used;
and whether the digest was receiver-recomputed.

`computed_by` values MUST agree with the receipt-level `receiver`, `adapter` and
`environment` identities. A receipt claiming provenance it does not carry is
invalid, not merely incomplete.

## 8. Receiver, adapter, environment

Unchanged from v1 §7, §8, §9. `receiver`, `implementation`, `adapter` and
`source_commit` remain distinct identities. `implementation_id` MUST NOT be used
as an implicit alias for `receiver_id` or `adapter_id`. No default identity
relationship exists between adapter and implementation.

## 9. Missing-value semantics

Unchanged from v1 §10 in intent:

```text
missing value ≠ UNKNOWN ≠ ABSENT
```

`null` remains prohibited. No field may use `null` as an implicit semantic alias
for `ABSENT`.

## 10. Explicit unresolved values

### 10.1 The v1 deficiency

v1 required `missing value ≠ UNKNOWN ≠ ABSENT` while prohibiting `null` and
providing **no representation for any of those states**. A v1 receipt therefore
could not record an unbound field at all. This is a schema deficiency, and it is
recorded here explicitly rather than resolved by omission.

It becomes material in v2 because `issuance_id` is a required field and **no
issuance record exists** in any in-scope repository against which a value could
be bound.

### 10.2 UnresolvedValue

```text
UnresolvedValue {
    state    ∈ { UNKNOWN, ABSENT, ERROR, REJECT }
    detail   non-empty string
}
```

These four states are recorded distinctly and are never collapsed into one
another, into `null`, or into a generic representation. `UnresolvedValue` is an
**engineering representation of an unbound field value**. It introduces no
protocol state and no normative requirement.

In v2 the **only** field whose value may be an `UnresolvedValue` is
`fixture.issuance_id`. Extending it to any further field is outside this
correction.

### 10.3 Transport

A bound value is transported as a JSON string. An unresolved value is
transported as a JSON object:

```json
{"detail":"…","state":"UNKNOWN"}
```

The two have different transport types, so a bound value can never be read as an
unresolved one, or the reverse. `null` and the empty string are rejected in both
cases.

### 10.4 Layer separation, unchanged

```text
raw_octets absent
```

MUST NOT be interpreted as:

```text
digest_output = ABSENT
```

These belong to different observation layers.

## 11. Schema invariants

### R-INV-01 — Fixture identity

`fixture.fixture_id`, `fixture.fixture_artifact_identity`,
`fixture.fixture_artifact_name` and `fixture.issuance_id` are required.
`fixture_artifact_identity` is a SHA-256 digest of the exact issued artifact
octets; a name is not an identity.

### R-INV-02 — Receipt provenance

`receiver`, `implementation`, `adapter` and `source_commit` identity are
required, at receipt level and per operand.

### R-INV-03 — Raw-material integrity

```text
SHA256(received.raw_octets)   == digest_operands.receipt_digest.value
SHA256(input_segment.octets)  == digest_operands.input_segment_sha256.value
```

### R-INV-04 — No conformance authority

The schema contains no `conformance_result` field and no equivalent
result-authority field. This is a structural authority-isolation invariant.

### R-INV-05 — Operand independence

The two digest operands are derived from separately recorded raw material by
separate calculation paths. Neither may be assigned, copied, or aliased from the
other or from any other previously computed digest. See §6.1.

## 12. Deterministic receipt serialization

Unchanged from v1 §12, extended to the v2 field set:

1. UTF-8 encoding.
2. Exactly the schema field names defined by BC-02.1 v2.
3. All schema fields are explicit; no implicit defaults.
4. Object member names are serialized in lexicographic order by Unicode code point.
5. No insignificant whitespace is emitted.
6. Strings use JSON string escaping only; no semantic normalization is performed by the receipt layer.
7. Integers are represented as JSON integers without leading zeroes or alternate numeric forms.
8. `received.raw_octets` and `input_segment.octets` use the explicit Base64 transport encoding defined in §6.4.
9. `null` is prohibited. An unresolved value uses the §10.3 form.
10. No additional fields are permitted.

Receipt serialization is an engineering representation of the receipt. It is not
a fixture representation and does not redefine fixture canonicalization or
digest-input rules.

### 14.1 The one relocation, declared explicitly

v1 `received.recomputed_sha256` is **not silently renamed**. Its v1 semantics are
explicit in v1 §6 and v1 R-VAL-005: *"explicitly receiver-derived from the
received raw octets"*. That is exactly the v2 `receipt_digest` operand, so the
binding is:

```text
v1  received.recomputed_sha256
        ≡
v2  digest_operands.receipt_digest.value
      with source = RECEIVER_RECOMPUTED
      and source_material = RECEIVED_BUFFER
```

The field is relocated rather than duplicated. Keeping a copy of the same value
in `received` would reintroduce, inside one receipt, the very read-one-field-twice
pattern this correction exists to remove.

No corresponding v1 field exists for `input_segment_sha256`. That absence is the
substance of PRE-01: v1 had one digest where B-VAL-014 requires two operands.

## 17. Definition of Done

BC-02.1 v2 is **CONSTRUCTED** when:

1. The two B-VAL-014 digest operands exist as separate fields.
2. Each operand records its own source material, calculation path and source.
3. Each operand carries an explicit provenance chain.
4. Aliasing between the operands is prohibited by invariant and impossible in the reference implementation.
5. Fixture identity, name and issuance identity are distinct fields.
6. UNKNOWN, ABSENT, ERROR and REJECT are representable without `null`.
7. Receipt state remains separated from conformance state; no authority-result field exists.
8. Deterministic receipt serialization is defined for the v2 field set.
9. v1, the executed v1 receipts, and the issued P-01 artifact are unmodified.
10. PRE-01-001…PRE-01-010 are recorded independently, with concrete evidence.
