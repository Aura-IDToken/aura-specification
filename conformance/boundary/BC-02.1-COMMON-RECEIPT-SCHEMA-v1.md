# BC-02.1 — COMMON RECEIPT SCHEMA v1

**Status:** CONSTRUCTED
**Parent:** BC-02 — Minimal Receiver-Side Handoff
**Purpose:** Common receipt representation for RI-PY and RI-RS.
**Conformance execution:** BLOCKED
**B-VAL-014:** NOT EXECUTED
**Normative authority:** NONE

## 1. Responsibility boundary

BC-02.1 represents the observation of a handoff:

```text
issued artifact
      ↓
   receiver
      ↓
   receipt
```

A receipt is an **evidence input**. It is not a conformance result.

BC-02.1 MUST NOT represent or derive PASS, FAIL, CONFORMANT, NON_CONFORMANT, acceptance state, digest-output state, §4.5 result, or B-VAL-014 result.

## 2. Schema identity

```text
schema_id      = BC-02.1-COMMON-RECEIPT
schema_version = 1
```

`schema_id` and `schema_version` identify this engineering schema. They do not identify a protocol version.

## 3. Canonical logical model

```text
BoundaryReceipt {
    schema_id
    schema_version

    fixture {
        fixture_id
        fixture_artifact_identity
    }

    handoff {
        status
        method
    }

    received {
        octet_length
        raw_octets
        recomputed_sha256
    }

    receiver {
        receiver_id
        implementation_id
        language
        implementation_version
        source_commit
    }

    adapter {
        adapter_id
        adapter_version
    }

    environment {
        environment_id
        platform
        runtime
    }
}
```

All fields above are required. BC-02.1 does not define implicit defaults.

## 4. Fixture identity

`fixture.fixture_id` and `fixture.fixture_artifact_identity` MUST both be present.

`fixture_artifact_identity` refers to the **issued artifact**, not to a logical object reconstructed by the receiver.

For P-01:

```text
fixture_id = FIX-DIGEST-P01
```

The schema MUST NOT substitute an identity derived from a parsed or reconstructed object, such as `hash(serialized_object)`.

## 5. Handoff state

`handoff.status` is a closed engineering domain:

```text
TRANSFERRED
NOT_TRANSFERRED
ERROR
```

The status describes handoff state only.

The following values are prohibited:

```text
PASS
FAIL
CONFORMANT
NON_CONFORMANT
```

`handoff.method` identifies the technical transfer mechanism. BC-02.1 does not establish a single transport as protocol-normative.

## 6. Received material

The `received` object records the material actually observed by the receiver.

```text
octet_length
raw_octets
recomputed_sha256
```

The central integrity invariant is:

```text
SHA256(raw_octets) == recomputed_sha256
```

where `raw_octets` means the octets actually received by the receiver.

The digest MUST NOT be computed from:

- expected hash;
- fixture description;
- parsed object;
- reconstructed JSON;
- textual hexadecimal representation;
- Base64 text representation.

### Raw-octet transport representation

The logical value of `raw_octets` is an octet sequence. For JSON receipt transport, BC-02.1 uses **Base64** as the explicit transport encoding of that octet sequence.

```text
JSON representation of raw_octets ≠ the octet sequence itself
```

The Base64 representation MUST decode unambiguously to the exact received octets. The digest is computed over the decoded octets, never over the Base64 characters.

`octet_length` MUST equal the number of decoded octets in `raw_octets`.

## 7. Receiver provenance

The receipt MUST preserve the following distinct identities:

```text
receiver
implementation
adapter
source_commit
```

The provenance chain is:

```text
fixture
   ↓
receiver
   ↓
implementation
   ↓
source_commit
```

`implementation_id` MUST NOT be used as an implicit alias for `receiver_id` or `adapter_id`.

## 8. Adapter identity

The adapter is an independent engineering artifact:

```text
adapter_id
adapter_version
```

No default identity relationship is established between adapter and implementation.

## 9. Environment

The receipt records execution context through:

```text
environment_id
platform
runtime
```

These fields support later execution-context reconstruction. BC-02.1 does not make a particular host, OS, or runtime a protocol-normative conformance requirement.

## 10. Missing-value semantics

BC-02.1 preserves the BC-01 distinction:

```text
missing value ≠ UNKNOWN ≠ ABSENT
```

No field may use `null` as an implicit semantic alias for `ABSENT`.

In particular:

```text
raw_octets absent
```

MUST NOT be interpreted as:

```text
digest_output = ABSENT
```

These belong to different observation layers.

## 11. Schema invariants

### R-INV-01 — Fixture identity

`fixture.fixture_id` and `fixture.fixture_artifact_identity` are required.

### R-INV-02 — Receipt provenance

`receiver`, `implementation`, `adapter`, and `source_commit` identity are required.

### R-INV-03 — Raw-material integrity

When `raw_octets` are present:

```text
SHA256(raw_octets) == recomputed_sha256
```

### R-INV-04 — No conformance authority

The schema contains no `conformance_result` field and no equivalent result-authority field.

This is a structural authority-isolation invariant.

## 12. Deterministic receipt serialization

The receipt has a deterministic JSON transport representation with these engineering constraints:

1. UTF-8 encoding.
2. Exactly the schema field names defined by BC-02.1.
3. All schema fields are explicit; no implicit defaults.
4. Object member names are serialized in lexicographic order by Unicode code point.
5. No insignificant whitespace is emitted.
6. Strings use JSON string escaping only; no semantic normalization is performed by the receipt layer.
7. Integers are represented as JSON integers without leading zeroes or alternate numeric forms.
8. `raw_octets` uses the explicit Base64 transport encoding defined above.
9. `null` is prohibited.
10. No additional fields are permitted.

Receipt serialization is an engineering representation of the receipt. It is not a fixture representation and does not redefine fixture canonicalization or digest-input rules.

## 14. Explicit exclusions

BC-02.1 does not define:

- acceptance_state;
- digest_output_state;
- expected_acceptance;
- expected_digest_output;
- §4.5 result;
- PASS/FAIL;
- RI-PY conformance;

- digest-input rules;
- new fixture classes.
