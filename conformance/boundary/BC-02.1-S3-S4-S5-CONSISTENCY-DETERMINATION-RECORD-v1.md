## A. PURPOSE

This record answers exactly one question:

> Do the existing authority sources and the existing evidence permit the
> construction of **one** consistent execution path across S-3, S-4 and S-5
> **without adding new normative semantics**?

It does not choose a semantics, does not change BC-02 or BC-02.1, does not
create a fixture, and does not prepare or authorize execution. Where an axis
cannot be closed from existing sources, this record says so and stops.

A determination of INCOHERENT is a statement about the **internal consistency of
the current semantic system**, not about any implementation, artifact or
conformance outcome. It is not a conformance failure, not a P-01 failure and not
a B-VAL-014 failure.

### A.1 Method

Every claim below is separated into five parts, per the analysis contract:

```text
SOURCE                 the artifact and section the claim rests on
OBSERVATION            what that source, or the corpus, actually shows
ENGINEERING CONSEQUENCE what follows for construction of an execution path
AUTHORITY STATUS       what authority level the source holds, if any
DETERMINATION          the consistency finding for that item
```

Declarations carried by task instructions, prior status lines, file names,
commit messages, existing receipts and computed digests are **not** treated as
authority unless the corpus grants them that status. An engineering contract is
not raised to normative authority; a normative source is not lowered to an
observation. A source that cannot be resolved is marked **UNRESOLVED / NOT
REACHABLE**, never as a settled fact of absence about the world.

## E. S-3 — INPUT-SEGMENT SEMANTICS

### E.1 Candidate S-3-A — transfer of an issued segment

```text
issued artifact
      │
      ▼
raw/input octets
      │
      ▼
allowed decode          (raw_input_encoding ∈ identity | base64 | base16)
      │
      ▼
input_segment_bytes
      │
      ▼
receiver
```

| Question | SOURCE | OBSERVATION |
|---|---|---|
| Which sources support this model? | BC-02 §4.2, §5.1, §5.2, §5.3, §6.1, §6.2, §6.3, §8 | The model is BC-02's own. §5.3: `input_segment_bytes = the octets of raw_input, after decoding raw_input_encoding`; `input_segment_sha256` is called *"the load-bearing value"* |
| Does BC-02 describe `raw_input` as execution input? | BC-02 §4.2 field table | **Yes, explicitly**: `raw_input` → *"the execution input — transferred as octets"*, marked *"Yes — the only execution input"* |
| Is `input_segment_bytes` the result of an allowed decode? | BC-02 §6.3 | **Yes.** Exactly one transformation is permitted; the decode MUST be total, deterministic, byte-exact, and *"MUST NOT be a JSON parse"*; encoding domain is closed to `identity`, `base64`, `base16` |
| Is parse / reconstruct / serialize forbidden? | BC-02 §6.1, §6.2 | **Yes.** `READ → HASH → FORWARD` is the only permitted pipeline; `parse → modify → serialize → execute`, re-serialization, canonicalization, transcoding and schema coercion are forbidden; a read-only view may never be a source of transferred content |
| Are `fixture_artifact_bytes` and `input_segment_bytes` distinguished? | BC-02 §5.1, §5.2 vs §5.3 | **Yes.** Three octet sequences are kept apart: `fixture_artifact_bytes`, `raw_input` (a field of the artifact), `input_segment_bytes` (its decode). §5.2 forbids applying canonical serialization to the artifact |

**ENGINEERING CONSEQUENCE.** S-3-A is fully specified as a *model* and is
internally coherent within BC-02. Its instantiation, however, requires an
artifact that **has** a `raw_input` field and a declared `raw_input_encoding`.

| SOURCE | C-25 (the artifact); corpus token census performed in this session |
|---|---|
| **OBSERVATION** | The P-01 artifact is `{"a":1,"b":"x"}` — fields `a` and `b`. It carries no `raw_input`, no `raw_input_encoding`, no `fixture_id` field, no `fixture_hash`, no `input_characterization` and no expectation segment. Across all remote branch tips of `aura-specification`, `raw_input_encoding` occurs in eleven paths — all contracts, records, or schema-layer code — and in **zero** fixture files. The other in-scope repositories return zero hits. |
| **ENGINEERING CONSEQUENCE** | Two readings are available for P-01 and **neither is declared by any source**: (a) the 15 octets are `fixture_artifact_bytes` and the artifact has no `raw_input`, in which case BC-02 §6.3's FIXTURE GAP clause applies and the handoff MUST be refused with `HANDOFF_REJECTED` / `ENCODING_INVALID`; (b) the artifact *is* the `raw_input` under `raw_input_encoding = identity`, so artifact ≡ input segment. |
| **AUTHORITY STATUS** | Reading (a) is a direct application of existing BC-02 text. Reading (b) is an **extension** of it: §6.3's decode operates on a `raw_input` field, and the contract contains no clause for an artifact that is its own input. Adding that degenerate case is a new declaration, i.e. new normative semantics at the layer that governs the boundary. |
| **DETERMINATION** | **S-3 binding for P-01: OPEN.** Recorded previously as PRE-01-G7 (C-18 §9) and as §N.4 of the terrain survey (C-21); re-verified here against the artifact and the corpus, unchanged. Not resolved by this record. |

## N. CONSISTENCY DETERMINATION

### N.1 The rule applied

COHERENT is available only if S-3, S-4, S-5, Registry, Issuance and BNC-1 can be
joined into one execution path **without**: new authority; change to existing
semantics; reinterpretation of the Registry; treating a non-issued artifact as
issued; treating a repository as a sealed store without the required
properties; or aliasing two operands.

### N.2 Condition-by-condition

| Condition | Satisfied? | Why |
|---|---|---|
| No new authority required | **NO** | The Registry is a consumed authority and is not reachable (§H); the chain has no origin (§L E1) |
| No change to existing semantics | **NO** | Instantiating S-3 on the only existing artifact requires extending BC-02 §6.3 to an artifact-only case (§E.1) |
| No reinterpretation of the Registry | **NO** — would be required | The only reachable candidate, APS-500, would have to be re-bound as BC-02's Registry (§H.2) |
| No non-issued artifact treated as issued | **NO** — would be required | Issuance authority and identity are not established (§G, §I) |
| No repository treated as a sealed store without the required properties | **NO** — would be required | Write denial not established; delivery was a shared read (§G.3, §D.2) |
| No aliasing of two operands | **NO** — would be required | Under the reachable v1 evidence there is one digest field; under S-4-A the two operands digest the same buffer per side (§F.2, §K.2) |

Six of six conditions fail. Any one of them is sufficient for the determination.

### N.3 Determination

```text
DETERMINATION:  INCOHERENT — CUSTODIAN DECISION REQUIRED
```

The existing authority sources and existing evidence **do not** permit the
construction of one consistent execution path across S-3, S-4 and S-5 without
adding new normative semantics.

The incoherence is of two distinct kinds, and they should not be conflated:

1. **Missing upstream authority** — Registry (§H) and issuance (§I). No
   construction at this layer closes these; they are authority acts.
2. **Internal non-joint-satisfiability** — BC-02 §5.3 / §7.1 / §14 / §15.3
   (CONFLICT-01). This one is not cured by supplying any artifact; it requires a
   determination of which value one operand carries.

### N.4 What this determination is not

```text
NOT a conformance failure
NOT a P-01 failure
NOT a B-VAL-014 failure
NOT a statement that P-01 was never issued
NOT a rejection of any existing evidence
```

The Controlled P-01 Handoff record and both receipts remain valid as recorded.
Both receivers did independently derive `ecf9e98e…d4e65667` over 15 octets
identical to the repository-resident artifact. Nothing in this record contradicts
that observation; what is unresolved is the semantic frame in which it would
count as transfer evidence.
