### I.5 Can the existing artifact be formally issued NOW? — NO, on four counts

Issuing it now would require, at minimum:

1. **A Registry entry to issue it from.** §15.2 step 1 is *"Resolve one Registry
   entry"*, and §4.2 sources `raw_input` *"From the declared Registry fixture
   artifact"*. There is nothing to resolve. Authoring the Registry is authoring
   a consumed authority — §D.
2. **A shape that §4.2 and §6.3 recognise.** The artifact is a bare payload with
   fields `a` and `b`. It carries no `raw_input`, so §6.3 has nothing to decode
   and §4.2 has nothing to pass to an adapter — §F, §N.
3. **An identified issuer.** §5.3 requires `input_segment_sha256` *"computed once
   by the issuer at seal time"*; §7.1 requires `fixture_artifact_identity`
   *"issuer-computed"*. No issuer identity is defined in any reachable artifact.
   An agent asserting an issuance would be asserting an authority act.
4. **A seal.** §6.4 requires structural write-denial before any transfer — §I.6.

Point 3 is the decisive one. An issuance record authored today over these octets
would be *either* an attestation that a past issuance occurred, which is false
and would launder the §I.2 provenance, *or* a fresh issuance event — which is an
exercise of issuing authority this task does not hold. **Both are refused.**

### I.6 The one requirement that is nearly dischargeable — recorded, not decided

BC-02 §6.4 admits a **content-addressed store** as an acceptable seal mechanism.
Git object storage is content-addressed, and the artifact's committed blob
`b45ffa980a1a776b6143d7fcb255fbfa8a436582` is immutable by construction: the
content of an existing object cannot be changed in place.

Against that: a **worktree** file at that path is freely writable, and §6.4 says
the artifact must be held *"in storage the boundary cannot write to"*. Whether
"the committed blob is the sealed artifact, and the worktree path is only a
materialisation of it" satisfies §6.4 is a **Custodian determination**. It is
recorded here as a candidate discharge, with both sides stated. **This report
does not decide it**, because deciding it silently would resolve a contract
question by implementation convenience.

### L.4 A material finding: as written, B-VAL-014 may not be able to catch BNC-1

BC-02 §8 states what the adapter receives: *"1. `input_segment_bytes` — an octet
buffer."* The decode of §6.3 therefore happens **issuer-side**; the receiver is
handed the segment already decoded.

BC-02 §7.1 then defines both operands over receiver-side material:

```text
raw_input_reference.input_segment_sha256   "hex SHA-256 of decoded octets
                                            — RECOMPUTED BY THIS RECEIVER"
receipt.receipt_digest                     "hex SHA-256 recomputed over the
                                            buffer actually received"
```

If the buffer actually received **is** the decoded segment, both operands are
SHA-256 over the same buffer on the same side. Apply BNC-1: flip one octet on
the RI-PY side only. RI-PY then records `H(corrupted)` in *both* operands, and
B-VAL-014's condition `receipt_digest == input_segment_sha256` **still holds on
that side**. The corruption surfaces only in B-VAL-012's cross-receiver conjunct,
`R_PY.input_segment_sha256 == R_RS.input_segment_sha256`.

Under that reading §15.3 cannot be satisfied as stated, because B-VAL-014 does
not catch BNC-1.

There is a second reading under which it does: §5.3 says the value is *"computed
once by the issuer at seal time"* and §7.1 carries `matches_issued_digest`. If
the record's `input_segment_sha256` is the **issuer-sealed** value echoed in,
and `receipt_digest` is the receiver's recomputation, then B-VAL-014 compares
receiver recomputation against issuer seal — and it catches BNC-1 exactly as
§15.3 requires. But that reading contradicts §7.1's own inline comment,
*"RECOMPUTED BY THIS RECEIVER"*.

**BC-02 §5.3, §7.1, §14 and §15.3 are therefore not jointly satisfiable without
a determination of which value `raw_input_reference.input_segment_sha256`
carries.** This is reported, not resolved. It is an authority-level question:
resolving it by implementation choice is precisely what §16.1 of the
reconciliation record forbade.

**Consequence for PRE-01: none requiring reopening.** BC-02.1 v2 marks both
operands `RECEIVER_RECOMPUTED`, implementing the first reading. Its
`DigestSource` domain already contains `EXTERNALLY_SUPPLIED`, which can carry
the issuer-sealed value if the Custodian selects the second reading. **v2
represents either outcome without redesign, without renaming any of the four
operand fields, and without collapsing the two paths.**

## N. 15-OCTET INPUT-SEGMENT BINDING

### N.1 The question

Are the 15 exact P-01 artifact octets themselves the input segment?

### N.2 Authoritative material located

BC-02 keeps three octet sequences apart (§5.1, §5.2, §5.3, §6.3):

```text
fixture_artifact_bytes   the artifact as issued, opaque octets
raw_input                a FIELD of the Registry fixture artifact, as issued, encoded
input_segment_bytes      decode(raw_input_encoding, raw_input)  ← the execution input
```

§4.2 sources `raw_input` *"From the declared Registry fixture artifact"* and
marks it *"the only execution input"*. §5.3 calls `input_segment_sha256` *"the
load-bearing value"*.

**The P-01 artifact has no `raw_input` field.** Its 15 octets are
`{"a":1,"b":"x"}` — fields `a` and `b`. Two readings are available and **neither
is declared anywhere**:

| Reading | Consequence |
|---|---|
| **(a)** The 15 octets are `fixture_artifact_bytes`, and the artifact carries no `raw_input` | §6.3's FIXTURE GAP condition applies: extracting an input would need `parse → re-serialize`, forbidden by §6.1, and BC-02 **MUST refuse the handoff** with `HANDOFF_REJECTED` / `ENCODING_INVALID` |
| **(b)** The artifact *is* the `raw_input`, issued under `raw_input_encoding = identity`, so artifact ≡ input segment | The handoff is admissible; `fixture_artifact_identity == input_segment_sha256 == receipt_digest == ecf9e98e…`; and B-VAL-014 degenerates further, per §L.4 |

### N.3 Status

**OPEN / UNRESOLVED.** No authority artifact specifies the relationship. This is
PRE-01-G7, raised at `31c238b` §9 and still unanswered:

> *"Treating the 15 artifact octets as the input segment is plausible but is an
> inference … **Left unbound.**"*

Does the existing BC-02 contract already provide a way to bind it **without**
normative change? **No.** §6.3's decode operates on a `raw_input` field; it has
no clause for an artifact that is its own input. Reading (b) is not a
application of existing text — it is an extension of it, and adding a
degenerate case to a frozen contract is a normative act. Reading (a) is
faithful to the text and rejects the handoff.

**Not silently invented.** No binding is adopted by this report.

### N.4 The exact question for the Custodian, and what turns on it

> For an artifact-only fixture with no `raw_input` field, are the artifact
> octets the input segment under `raw_input_encoding = identity` (reading b), or
> does §6.3's FIXTURE GAP clause apply and the handoff be refused (reading a)?

Turning on it: DEP-003 / VE-03 (§F, §M); whether a controlled re-handoff of P-01
is admissible at all; the `raw_input_encoding` value both v2 receipts would
carry; and — via §L.4 — whether B-VAL-014 retains any discriminating power for
this fixture.

### N.5 PRE-01 compatibility — reviewed, not reopened

BC-02.1 v2 records `input_segment` and `raw_input_encoding` as **fields**, and
takes no position on which reading holds. It can represent (b) directly. Under
(a) no v2 receipt would be produced at all, because the handoff would be
refused — which v2's `handoff.status` domain already expresses. One compatibility
point is recorded for the Custodian, and it is a question, not a defect: v2
documents the decode as applied **at the receiver**, whereas BC-02 §8 hands the
receiver an already-decoded segment. Under `raw_input_encoding = identity` the
two models coincide exactly. Under a non-identity encoding they do not, and the
Custodian's answer to §L.4 settles which model v2's `input_segment` block
records. **No v2 field is renamed, removed, or re-scoped by this report.**
